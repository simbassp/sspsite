# Обновление серверной авторизации

## Что меняется

Сервер больше не использует `ssp_session` как подтверждение входа или источник прав.
Эта cookie остаётся только кэшем отображения для существующих клиентских компонентов.
Даже если изменить её ID, роль, права или подразделение, сервер проверяет реальную
Supabase-сессию через `auth.getUser()` и загружает активный профиль по подтверждённому
`auth_user_id`. Роль и отдельные разрешения берутся из базы при каждом запросе.
Старый общий кэш проверки по ID удалён. Ошибки проверки не разрешают доступ.

`@supabase/ssr` хранит и обновляет Supabase-токены в cookie, общих для браузера и
сервера. Эти cookie доступны клиентскому SDK по его стандартной схеме; защита
основана на проверке настоящего токена в Supabase Auth, а не на доверии содержимому
cookie. Proxy сохраняет обновлённые токены также при перенаправлениях и исправляет
отображаемые данные старой cookie из подтверждённого профиля.

Регистрация по приглашению и без подтверждения email сохраняется. Восстановление
пароля остаётся отдельным существующим потоком.

## До публикации

- Проверить в тестовой среде вход сотрудником и администратором, выход и повторный
  вход, восстановление пароля и регистрацию по приглашению без подтверждения email.
- Серверу нужны уже используемые `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. Новые секреты и
  миграции для этого PR не нужны. Секреты не добавлять в GitHub.
- У действующих профилей должен быть правильный `app_users.auth_user_id`.
  Автоматическая перепривязка чужого профиля только по совпавшему логину удалена.
  Для старой записи без связи с Auth исправлять привязку следует вручную после
  проверки владельца, а не доверять переданному пользователем ID/логину.
- Предупредить пользователей: старой cookie недостаточно, после обновления нужно
  войти заново. Аккаунты, пароли и результаты тестов не удаляются.

## Проверки

```sh
npm ci
npm run test:auth
npm run build
```

Автоматические проверки используют настоящий SDK Supabase SSR и исходные
обработчики с изолированной имитацией Auth/REST. Они не отправляют запросы к
рабочей базе. Покрыты подмена cookie, права сотрудника и администратора, изменение
прав, деактивация, ошибки Auth/БД, обновление токена и перенос cookie при редиректе,
вход без подтверждения email и доступность страницы восстановления.

## Публикация

После проверки и принятия PR в `main`, на компьютере с доступом по SSH к серверу:

```powershell
cd "C:\путь\к\sspsite"
git switch main
git pull --ff-only origin main
.\deploy.ps1
```

Этот PR сам по себе не обновляет рабочий сервер. Существующий скрипт пересобирает
приложение и перезапускает PM2; возможен короткий перерыв. Если GitHub недоступен
серверу, у скрипта есть существующий режим `-LocalSync`.

После обновления проверить:

1. Без входа защищённые страницы перенаправляют на `/login`.
2. Сотрудник открывает обычные разделы, но получает 403 на
   `GET /api/admin/tests/final-closure`, в том числе после изменения `ssp_session`.
3. Настоящий администратор получает 200 на тот же запрос.
4. После выхода защищённые разделы снова требуют входа.

Проверка реальных аккаунтов и действующего Supabase остаётся этапом тестовой
публикации: локальные автоматические проверки не заменяют её.

## Граница исправления

PR закрывает доверие сервера к подменяемой cookie и связанные ошибки сессии.
Проверка баллов и времени итогового теста на сервере, обработка ошибок сохранения
результатов и пересмотр RLS из отдельного аудита остаются отдельной работой.
Не откатывать этот PR на рабочем сайте без понимания, что прежний обход прав вернётся.
